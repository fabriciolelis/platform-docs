# ADR-009: Observability stack for the Release 1 SLOs

- Status: Accepted
- Date: 2026-11-18

## Context

The four Release 1 SLOs (README) cannot be measured yet: the API exposes no
metrics, nothing probes `/ready`, and the ingestion signal
(`runbooks/daily-import.md`) is not collected. The Sprint 4 spec
(platform-docs#32) left four decisions open: the monitoring stack, how it is
packaged given ADR-008, the metrics library in the API, and whether alerting
is part of Sprint 4.

The stack must run next to Argo CD, PostgreSQL, and the API on a laptop k3d
cluster (about 8 GB of memory for Docker), be deployed through GitOps like
everything else (ADR-003, ADR-008), and stay readable for a portfolio
reviewer. Only one service is monitored.

## Decision

- **Stack:** Prometheus, configured directly (a Deployment with our own scrape
  configuration and recording rules), plus two standard exporters:
  **kube-state-metrics**, which turns Kubernetes object state into metrics and
  so carries the ingestion signal (Job status), and the **blackbox exporter**,
  which runs the synthetic probe on `/ready`. Each SLO is a recording rule and
  one documented query, read in the Prometheus UI.
- **Packaging:** all components are deployed with Kustomize, from upstream
  images and our own manifests, as a separate Argo CD Application per
  environment. ADR-008 is unchanged: no Helm.
- **Metrics in the API:** **OpenTelemetry**: the SDK, the FastAPI
  instrumentation, and the Prometheus exporter, which serves the metrics for
  Prometheus to scrape. HTTP metrics follow the OpenTelemetry semantic
  conventions: request duration as a histogram, labelled by route template and
  exact status code. Its default buckets for request duration include 0.5 s,
  the latency SLO's threshold. Health, readiness, and metrics endpoints are
  excluded from instrumentation.
- **Dashboards:** none in Sprint 4. A dashboard tool is reconsidered with the
  portfolio-facing work in Sprint 5.
- **Alerting:** not in Sprint 4. Alerts are defined with the first persistent
  environment, when someone can act on them.
- **Pinned versions** (each at least two weeks old when chosen): Prometheus
  v3.15.1, kube-state-metrics v2.19.1 (the release built for Kubernetes 1.35),
  blackbox exporter v0.29.1, OpenTelemetry SDK 1.45.2, and the OpenTelemetry
  FastAPI instrumentation and Prometheus exporter 0.66b2.

## Alternatives considered

- **kube-prometheus-stack** (Prometheus Operator, Prometheus, Alertmanager,
  Grafana, node-exporter, and many default dashboards and alerts): the most
  common bundle, but around 1 to 1.5 GB of memory on a laptop, dozens of CRDs,
  most of it unused here, and only available as a Helm chart, which ADR-008
  rejected.
- **Prometheus Operator** without the bundle (`ServiceMonitor`,
  `PrometheusRule`, and `Probe` resources): the usual pattern once several
  services are monitored, but an operator and its CRDs are more moving parts
  than one service needs. It is the evolution path for this decision.
- **VictoriaMetrics:** lighter and compatible with PromQL, but less widely
  recognized, and its query language differs in subtle ways.
- **`prometheus-client` with our own middleware:** the most used Python
  metrics library, one stable dependency and about 30 lines of code, but
  metrics only. **`prometheus-fastapi-instrumentator`:** the most used
  FastAPI wrapper, with less code, but metrics only and defaults that group
  status codes. OpenTelemetry was chosen as the open standard for metrics,
  traces, and logs, so tracing can be added later without instrumenting again.
- **Grafana now:** a visual SLO dashboard, but about 200 MB more and another
  component, while each SLO is already one query.
- **Alerting rules or Alertmanager now:** with no always-on environment and no
  one on call, alerts would fire to nobody.

## Consequences

- The stack is small: three components, all in plain manifests the validator
  already understands, with no new resource kinds to add schemas for.
- Estimated footprint on the local cluster, as starting requests and limits to
  tune with measurements: Prometheus 256 Mi to 512 Mi, kube-state-metrics 64 Mi
  to 128 Mi, the blackbox exporter 32 Mi to 64 Mi, so about 700 Mi at the
  limits, compared with the 1 to 1.5 GB of the bundled alternative.
- The scrape configuration and recording rules are written and reviewed by
  hand in a ConfigMap; there are no operator conveniences.
- The OpenTelemetry FastAPI instrumentation and Prometheus exporter are Beta.
  Pinned versions limit surprises; their upgrades go through review like any
  dependency. The exporter itself depends on `prometheus-client`.
- Metric names follow OpenTelemetry's conventions (for example
  `http.server.request.duration`, exposed to Prometheus with a unit suffix),
  not names chosen by us.
- Moving to the Prometheus Operator later means replacing the scrape
  configuration with `ServiceMonitor` and `Probe` resources; the metrics and
  queries stay the same.
- Implementation is tracked in platform-gitops#15, #16, #17 and
  formula-insights-api#38.
