# ADR-007: Manage the database schema with Alembic migrations

- Status: Accepted
- Date: 2026-10-25

## Context

The API and the importer create their tables with SQLAlchemy `create_all` at startup (ADR-005). `create_all` only creates missing tables and never changes an existing one. A schema change, such as a new column or a nullability change, would be skipped on any existing database, and the code would then fail at runtime. Nothing records which schema version a database is on.

That was acceptable for throwaway local databases in Sprint 1. It is not acceptable once a database must persist across releases, which starts with the first GitOps-managed environment (ADR-003). There, a new version rolls out while the previous version is still running, so for a short time two versions of the code share one schema, and the previous image must stay deployable for rollback.

## Decision

- **Tool:** schema changes are versioned migrations managed with **Alembic**. Migrations live in the formula-insights-api repository and ship in the same container image. A baseline migration creates the current schema; `create_all` is no longer called by the API or the importer.
- **Drift check:** CI runs `alembic check`, which fails when the models change without a matching migration. Generated migrations are reviewed like any other code.
- **Who runs migrations, and when:** a dedicated step applies migrations (`alembic upgrade head`) **before** the new version rolls out. The API and the importer never migrate. In Kubernetes this step is a Job using the release image, run as an Argo CD PreSync hook; if it fails, the sync stops and the running version is untouched. Locally, it is one documented command run before starting the API or importing.
- **Compatibility (expand, then contract):** every migration must work with the version currently running. New tables and columns are added first (new columns nullable or with a default); code stops using an old column in one release, and the column is dropped or renamed in a later release.
- **Rollback (roll forward):** a faulty migration is fixed by a new migration. Downgrade scripts may exist, but are not tested and are not part of any rollback procedure. Rolling back means deploying the previous image, which the compatibility rule keeps working against the newer schema.
- **Existing databases:** only local and CI databases exist today, so they are recreated from the baseline and re-imported (imports are idempotent). A future database that holds data that cannot be recreated is brought under migration control with `alembic stamp` after its schema is verified against the baseline.
- **Database roles:** migrations run with a migration role that may change the schema; the API and the importer use an application role that may only read and write rows. The roles are created with the first persistent environment (Sprint 3); until then, local and CI databases use a single role.

## Alternatives considered

- **Flyway or Liquibase:** plain-SQL, language-neutral migrations. Rejected because they need a JVM or a second image, and they cannot compare the SQLAlchemy models with the database, so the drift check would be custom work. They fit better when several services in different languages share a schema.
- **Atlas:** declarative schema-as-code with migration linting. Rejected as a new ecosystem with some features behind a paid service, and uncommon with SQLAlchemy.
- **Migrating at API startup:** rejected because replicas race to apply the same migration, the API would need schema-changing rights, and a failing migration would crash-loop every new pod.
- **Init container in the API Deployment:** rejected because it runs once per pod, with the same races, and does not cover the importer CronJob.
- **Tested downgrade scripts:** rejected because a downgrade cannot restore data removed by the migration it reverses, and rarely used code tends to be broken when needed. The compatibility rule makes an application rollback safe without them.
- **One database role for everything:** rejected because the API would keep rights to alter and drop tables, against the least-privilege rule in the formula-insights-api README.

## Consequences

- Every database reaches the same schema the same way, and its version is recorded in the database.
- A model change without a migration fails CI.
- Removing or renaming a column takes at least two releases; reviews must check that each migration is compatible with the running version.
- The release process gains a migration step that must run before the rollout; its Kubernetes manifest is part of Sprint 3 (platform-gitops#2).
- There is no schema undo; mistakes are corrected forward with a new migration.
- Until Sprint 3, local and CI databases use one role, so least privilege is not yet exercised there.
- Implementation, including the baseline migration, the documented command, and running migrations in CI, is tracked in formula-insights-api#18.
